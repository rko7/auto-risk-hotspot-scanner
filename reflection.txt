For this assignment, the part that took me the most time was debugging the backend query filters, especially the `where` clause for the date range and the division filter.
I initially thought my app was failing to return data because the API was not accepting my date values, and I also got confused when I saw cases where `DIVISION` and `DISTRICT` did not match what I expected, so I spent about a week investigating whether the problem was my code or the source dataset structure.
After testing and checking the returned data more carefully, I confirmed it was mostly a data interpretation issue rather than a broken filter.
A key step in resolving this was my commit `c0dc65f` (“Refactor ArcGIS date filtering and division SQL logic”), where I reworked the date filtering and division query logic to better match the ArcGIS/TPS dataset behavior.
Another important step was commit `19a0b2a` (“improve responsive form layout and add latest first sorting”), where I improved the responsive form layout after multiple attempts and made the results more practical to read by showing the latest records first.
I also added an optional severity filter and CSV export in commit `114f764` (“add severity filter and csv export with latest default date range”), which made the app more useful as a filterable search tool and a small reporting aid.
The hardest implementation part for me was the frontend layout and responsive arrangement because I kept changing the form structure (especially the Severity field), and the layout would look fine at one width but break at another width.
I eventually grouped the fields in a more stable way, even though I am still not fully satisfied with the Search button placement, and I continued making small UI polish changes afterward (for example, `5f52104`).
I also added a dynamic “available dataset date range” note and set the date inputs to default toward the latest available dataset range, which was inspired by a date-handling pattern I used during a co-op data visualization/reporting task where displayed dates had to update automatically to the most recent available data.
Even though the debugging delay reduced how much time I had for extra features, I was still able to add a simple severity distribution bar chart summary in commit `45a0ad9` (“add severity bar chart”), which helped the results section look more professional and easier to scan quickly.
Originally, I wanted to make the UI more feature-rich by expanding the chart and adding additional summary visualizations.
However, as I added more features, I frequently ran into conflicts with the existing code, where layout or logic would break and require additional time to stabilize.
Because I did not have enough time left to thoroughly test and refactor those additions, I chose to prioritize a stable end-to-end workflow over adding more complex or flashy features.
While polishing the UI, I also added success and error feedback messages using toast notifications in commit `0c2d823` (“add toast alerts for success and error states”).
I have seen this type of message many times on modern websites and in tools I use at work (for example, the Umbraco backoffice), but I used to assume it was just a type of modal.
During this assignment, as I kept adding and refining features, I looked into how this pattern is normally implemented and learned that this style of temporary notification is commonly called a “toast.”
Overall, this project reinforced how important it is to validate assumptions early when working with external datasets, especially when field meanings do not map cleanly to real-world expectations.
It also reminded me that UI improvements often take longer than expected because small layout changes can have side effects across different screen sizes.
If I had more time, I would focus next on adding richer visual summaries and refactoring the UI logic to make new features easier to add without breaking existing behavior.
